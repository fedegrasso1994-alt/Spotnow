# Soma — Observability MVP contract

Staging only: `zjinjtkekmaqtxsuyvho`, branch `codex/soma-schema-v2-staging`. Audit baseline `b550f27`. Founder decisions supersede the original audit's open questions: operational diagnostics **14 days**, approved candidate thresholds, automatic email destination explicitly `somadatingapp@gmail.com`, no second recipient. No reusable application email transport is evidenced in the repository. Auth SMTP and the manual Gmail inbox are not reused as a runtime mailer. No provider/credentials introduced; **email remains hard OFF**. A future authorized transport integration and delivery test are required before pilot.

## Boundary and privacy model

Migration 053 adds only private operational tables and scoped RPCs. `ops_control` is OFF by default, test_only=true. `ops_admission` admits explicit synthetic random request IDs during tests: ordinary existing users/requests are ignored. Ordinary collection cannot start unless `purge_ready` has been explicitly attested; this is a rollout gate, not proof of a running purge scheduler.

Closed fields in `ops_events`: technical sequence ID, random request ID, operation enum, source client/edge/job, result enum, error class enum, bounded duration and server creation timestamp. No account ID is necessary or collected. No names/email/phone, URLs, routes/query/referrer, device IDs, content IDs/pairs, Place/GPS, preferences, bodies, errors/stacks, tokens, push keys or headers are stored. The sequence supports deterministic event ordering, not user tracking. Input validation happens before insertion; no arbitrary metadata object or caller-provided timestamp is accepted. `ops_recent` exposes only the safe operational projection.

Client responses may be inspected transiently and bounded to classify known SQL/API codes or fixed technical phase markers. The raw error, message, request body and response body are never persisted in diagnostics. A known DD allocator error, Match constraint or moderation-audit relation failure can be labelled with that coarse phase. Unknown inner transaction failures remain at the outer operation: do not invent a phase or anonymous author relationship.

Taxonomy: validation_error, authorization_error, conflict_error, dependency_error, timeout_error, internal_error. Results additionally distinguish expected_off and cancelled. Normal unavailable/neutral social results remain success; no hidden romantic suppression reason is logged. No body of a successful product response is read by client observation. Edge job summaries read only bounded existing JSON results to detect failed/uncertain/permanent counts despite HTTP 200. No raw summary is copied into the operational table.

Observation errors cannot replace product results. Collection is best effort, bounded, with no persistent client queue or cross-session tracking. Existing business nonce, quota, authentication, timeout, eligibility, publication, PHOTO decoder/lifecycle, Share and Match rules stay unchanged. An active anonymous block is not reinterpreted or logged as a named relationship.

## Instrumented paths

- Shared Supabase transport: Auth login/signup/OTP/token/verify, callback failure marker, user/session bootstrap; photo profile writes/signing; DD public read and known allocator phase; ORA presence/read/Spot; TRIBE Spot; SPOTTED post/comment/QoD/request/decision/Share; chat write/read; subscription/revocation; Analytics observation; report and moderation mutations. Refresh-token requests are bootstrap, not a new signup metric; logout/settings are not labelled login.
- Explicit Edge boundaries: upload, JPEG/PNG/WebP canonical worker, signed photos, delete-account, lifecycle collector, notification check/dispatch/prune, privacy retention. Only the Deno entry points are wrapped: processing/validation and lifecycle implementations remain byte-identical.
- Manual `operations` Edge: service-only, fixed Analytics purge or diagnostic purge, no scheduler or arbitrary RPC/target. Gateway JWT remains ON plus exact service credential authorization in the handler. No browser can execute a purge through this endpoint.
- Existing PHOTO request/lease/receipts and notification outcomes are reused for diagnosis, not copied wholesale. Analytics fail-open `dropped` remains a separate best-effort counter shown in the health view; this is not an exact ingestion-error timeline.
- Runtime error/unhandled/bootstrap/callback signals contain only enums. Existing offline fallback records a single tab-local boolean; after a subsequent successful load the app may report fallback activation and clears the marker. No protected response is cached. `public/sw.js` is unchanged. Existing clients with an older cached offline HTML may not emit this signal; there is no claim of universal offline detection or proof of a new false-offline defect.

## Correlation and trust

Client generates a random ID per HTTP attempt. Existing `sb-request-id` is retained when valid; UUIDv7 gateway IDs are accepted. Edge requests use `x-soma-request-id`; response and CORS expose that ID. PHOTO's business `X-Photo-Request-Id`/nonce remains independent and unchanged. The actual hosted PHOTO negative request verified the same diagnostic ID in response and server event.

PostgREST RPC responses can be correlated at the HTTP/client observation boundary. No guarantee is made that a random app ID reaches every DB statement or provider log. No product RPC arguments were added for telemetry. Rolled-back transactions cannot preserve an INSERT log in the same transaction, so client/Edge boundaries observe their outcome separately. Inner Match/audit/allocation attribution is available only for recognized technical codes; otherwise inspect the outer request and existing authorized diagnostics. Auth provider internals, database outages and log-drain integration remain provider/manual coverage limits, not fabricated server traces.

Client events are explicitly **untrusted**. They cannot impersonate edge/job sources, create server incidents or mark a server incident recovered. Only service-role `ops_record_server` can record authoritative boundary events. Successful server retries set last_success_at on an open incident, without erasing the original failure. No request ID grants authority. Client flood is capped separately (1,000/hour); edge/job caps are 25,000/hour/source. Dropped counts expose coverage loss, not product throttling. There is no IP/device/account fingerprint for telemetry rate control.

## Alert rules and email

Private incidents are deduplicated by operation/source while open. Three consecutive unexpected failures in ten minutes create a warning; spike requires at least five unexpected failures, at least twenty attempts and at least 20% errors in ten minutes. Two consecutive unexpected failures of an observed active job create a job incident. Validation, authorization, conflicts, cancellation and intentionally OFF results do not create these incidents. Client signals are consultable but cannot trigger authoritative incident generation.

An incident stores operation/source, categorical rule, status, server times, occurrence counter, last successful retry and email_state=disabled_provider. It contains no recipient address or content. Further failures update that incident, rather than creating one per retry. Successful retry remains distinguishable; it does not silently erase the history or automatically promise resolution. Read-only UI does not introduce an incident-management/appeal workflow. Metadata is physically purgeable after fourteen days, including open incidents; longer incident evidence requires the separate approved incident/safety procedure, not an indefinite operational exception.

Email cannot be enabled through a forgotten flag: DB constraint keeps it false. The approved recipient is a **future explicitly authorized destination**, not an implicit reuse of support. No SMTP fallback, webhook, push or test email was sent. Before pilot: select/configure authorized sender transport, review access/TTL/provider implications, define send/retry/dedup/recovery behaviour and verify receipt to the approved recipient. No substitute recipient is assumed.

## Health and jobs

`?health=1` is a small private operational view, separate from Analytics. Server access requires existing active ADMIN plus verified MFA/AAL2; normal users, MODERATOR-only, missing factor, revoked role and logout are denied. The frontend flag/route alone grants nothing. Views and request-ID lookup are bounded to recent safe records and cleared on logout/account/session change/page hide. No raw database browser is needed for the recent incidents.

Ten health groups: Auth, API/Edge, Storage/Photo, TRIBE/DD, ORA, SPOTTED, Match/Chat, Notifications, Analytics jobs, Moderation. No measurement yields unknown, not healthy. Server failures yield degraded; disabled features are intentionally off. Positive boundary evidence does not claim complete provider health. Client failure counts are labelled unverified. Job entries can be healthy only for a recently observed successful configured job; stale/failing/off/not-configured/unknown are distinguished.

Job state supports last_success, last_failure, class, duration, consecutive failures and next expected execution where known. PHOTO cleanup and privacy-retention's existing configured cron cadence is one minute; both remain OFF. Notifications dispatch/prune, Analytics purge and diagnostic purge have no invented cadence. With a configured interval, more than two intervals after the last observed run is degraded. Never-run/no-anchor jobs remain unknown; no heartbeat is fabricated. A cron HTTP send does not prove downstream outcome. No PHOTO unknown/review writer is purged because of age, and no scheduler is activated.

## Retention and operational gates

Events, admission, incident and job metadata have a **14-day operational horizon**. Reads exclude older records. `ops_purge(true)` is dry-run; false physically deletes due records in bounded batches (events/incidents 1,000 per call), repeated to exhaustion. Jobs' expired technical state is also removed. Policy/configuration rows contain no account history. New logging does not change Analytics 90-day/24-month or any existing product/safety/PHOTO retention.

No purge scheduler has been installed or enabled. Ordinary collection stays OFF until an explicit monitored purge cadence is proven and purge_ready attested. A callable purge alone is not automatic enforcement of a fourteen-day deadline. The hosted synthetic expiry/purge test demonstrates physical deletion and retry safety, not operational scheduling readiness. Provider-generated Auth/DB/Edge/CDN logs have separate plan/configuration-dependent TTL and may include IP/UA/context: their actual fields, retention and access remain manual PROVIDER/INCIDENT checks. This contract does not promise to retroactively remove vendor logs.

Pause: ops_control.enabled=false; frontend VITE_OBSERVABILITY_MVP OFF; keep email and all existing feature/job controls OFF. No destructive rollback, no restoration of legacy PHOTO writers, no permission widening and no deletion of current product evidence. New schema may remain inert. Never use source=client as security proof or turn currently OFF product features ON to obtain green health status.
