## Precise code-path analysis

`public/sw.js` intercepts only same-origin GET navigations. It runs:

`fetch(event.request).catch(async () => caches.match('/offline.html') || static503)`

That catch is the only path in these handlers serving the full static **“Sei offline”** document. HTTP 302/401/403/500 responses alone do not enter it. The prior screenshot therefore identifies the fallback branch, but does **not** identify why the browser fetch promise rejected. There is no captured exception type/message or request trace from the historical failure. A Vercel protection redirect, a browser transport limitation or cancellation must not be presented as a proven cause.

The static offline document does not bootstrap Auth or dynamic imports. Auth/router code does not generate this document. Their involvement upstream of a failed navigation is not established. In this run Auth/bootstrap and Match resolution succeeded for the active session.

`public/notification-runtime.js` currently does not call `clients.matchAll`, `client.navigate` or `focus`. The click handler closes the OS notification, reads its local binding, rejects stale/malformed data and calls only:

`clients.openWindow(new URL('/?n=' + reference, self.location.origin).href)`

No private target URL is accepted from the payload; the app reauthorizes the reference using the current owner session. There is no implemented focus→navigate race to fix. A failure in `openWindow` itself does not execute the navigation-fetch catch in this code; the subsequent browser navigation is a separate layer. Real `openWindow` behaviour was not measured because no OS notification was available. VM execution of the actual click handler verifies normalization, stale binding rejection and repeated-click behaviour; this is not a claimed real OS tap.

**Root cause: unresolved. Fix: none applied.** SW fetching, offline support, Deployment Protection, authentication and notification product semantics remain unchanged. No retry loop or cache workaround was added.
